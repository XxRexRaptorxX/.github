## 📋 Before Contributing

Before starting to work on a contribution:

- Check the existing issues and pull requests to avoid duplicate work.
- Make sure your changes are relevant to the project.
- Discuss larger changes or new features before implementing them.
- Make sure you understand the project's code structure and existing conventions.
- Read the repository's `LICENSE.md` before contributing.

For questions or help, feel free to contact me on [Discord](https://discord.com/invite/ycRJJk8EXV).

## 🔀 Pull Requests

Contributions should be submitted through GitHub Pull Requests.

A good pull request should:

- Have a clear and descriptive title.
- Explain what was changed and why.
- Focus on one specific feature, fix, or improvement.
- Include relevant information about the changes.
- Be tested before submission.
- Avoid unrelated changes or unnecessary formatting modifications.

Please make sure your changes work as intended and do not introduce new issues.

If your contribution fixes an existing issue, reference it in the pull request description (e.g. `Closes #123`).

## 📝 Commit Messages

All commits should follow the **Conventional Commits** specification.

This keeps the commit history consistent, readable, and easy to understand.

### Format

`<type>(<scope>): <description>`

The scope is optional.

### Common Types

| Type | Description |
| --- | --- |
| `feat` | Add a new feature |
| `fix` | Fix a bug |
| `docs` | Documentation changes |
| `refactor` | Code restructuring without changing behavior |
| `perf` | Performance improvements |
| `test` | Add or update tests |
| `build` | Build system or dependency changes |
| `ci` | CI/CD configuration changes |
| `chore` | Maintenance and other tasks |
| `revert` | Revert a previous commit |

### Examples

```text
feat: add new dungeon structure
feat(worldgen): add underground generation
fix: resolve crash when opening the config screen
fix(items): correct item durability
docs: update installation instructions
refactor: simplify structure generation
perf: optimize block entity ticking
chore: update dependencies
```

### Important Rules

- Use the appropriate type for your changes.
- Write short, descriptive commit messages.
- Use the imperative mood (e.g. `add`, `fix`, `update`).
- Do not use vague messages like `changes`, `update stuff`, or `fix`.
- Separate unrelated changes into different commits.

For breaking changes, use `!` after the type or scope:

`feat!: change the configuration format`

For more information, see the [Conventional Commits specification](https://www.conventionalcommits.org/en/v1.0.0/).
